\chapter{Программно-аппаратная реализация навигационной системы}
\label{chap:implementation}

В данной главе детально описывается архитектурная и низкоуровневая программная реализация высокопроизводительной навигационной системы. Рассматриваются принципы Data-Oriented Design, методы векторизации вычислительного ядра, структура Модуля принятия решений (МПР), а также интеграционная инфраструктура сетевого взаимодействия и графического интерфейса.

\section{Архитектура вычислительного ядра и управляющего контура (МПР)}

Разработанная система построена по модульному принципу с жестким разделением вычислительного (микросекундного) и управляющего (миллисекундного) контуров. Основными компонентами системы являются:

\begin{enumerate}
    \item \textbf{Симуляционная среда (TrafficEngine):} осуществляет ведение физического времени, обновление координат агентов (\texttt{FullAgent} / \texttt{FluidAgent}) и расчет скоростей на ребрах в соответствии с LWR-моделью.
    \item \textbf{Асинхронный модуль принятия решений (MprEngine):} управляющий слой, осуществляющий интеллектуальное регулирование транспортных потоков.
    \item \textbf{Вычислительное ядро (TdAltRouter):} stateless-оракул, выполняющий многопоточный поиск динамических путей.
\end{enumerate}

Связующим звеном выступает асинхронный МПР, который решает задачу предотвращения вычислительного затора (Thundering Herd) и стабилизации динамических весов. МПР реализует следующие механизмы регулирования:

\begin{itemize}
    \item \textbf{Регуляризация ландшафта (Hysteresis):} Для предотвращения хаотических колебаний путей при микроскопических колебаниях трафика, агент инициирует перестроение исключительно в случае, если ожидаемый выигрыш по времени превышает $\Delta T \ge 15\%$ от текущего ETA. При этом старый маршрут транзакционно удаляется из корзинок посредством \texttt{fetch\_sub}, а новый резервируется через \texttt{fetch\_add}.
    \item \textbf{Управление частотой опроса (Token Bucket):} МПР ограничивает интенсивность запросов к роутеру на уровне $5\%$ от общего числа активных агентов в секунду, распределяя их равномерно с помощью алгоритма маркерного ведра.
    \item \textbf{Локальное перестроение (Sub-route Patching):} В случае обнаружения затора на длинном маршруте МПР не пересчитывает путь полностью. Роутер выполняет сверхбыстрый локальный поиск от текущей позиции агента до транзитного узла, расположенного за пределами пробки (на расстоянии 5–10 км), после чего МПР бесшовно встраивает новый сегмент в существующий массив вейпоинтов в \texttt{RouteArena}.
\end{itemize}

\section{Применение Data-Oriented Design и оптимизация кэш-памяти}

Для преодоления барьера пропускной способности памяти (Memory Wall) структуры данных были полностью перепроектированы от классического объектно-ориентированного подхода (AoS) к компонентному, ориентированному на данные (DoD / SoA).

\subsection{Сжатое разреженное строчное представление топологии (CSR)}
Вместо связных списков объектов узлов и ребер с указателями, вызывающими хаотичные промахи кэша (Cache Misses) при обходе графа, топология дорожной сети представлена в виде двух плотных непрерывных массивов:
\begin{itemize}
    \item \texttt{row\_ptr} (размером $V + 1$): хранит смещение первого исходящего ребра для каждого узла;
    \item \texttt{col\_ind} (размером $E$): хранит идентификаторы целевых узлов смежности.
\end{itemize}
Это гарантирует последовательное чтение памяти и позволяет процессору эффективно задействовать аппаратную предвыборку данных (Hardware Prefetching). В горячем цикле обхода принудительно вызывается инструкция превыборки следующей строки:
\begin{code}{code:prefetch}{C++}{Принудительная предвыборка строки кэша для CSR}
_mm_prefetch((const char*)&row_ptr[u+1], _MM_HINT_T0);
\end{code}

\subsection{Thread Affinity (CPU Pinning)}
Для предотвращения накладных расходов планировщика ОС Linux на миграцию потоков между ядрами процессора Ryzen 5 5600H, каждый из 12 вычислительных потоков жестко привязывается к конкретному логическому ядру при инициализации пула:
\begin{code}{code:affinity}{C++}{Жесткая привязка потоков Thread Affinity}
cpu_set_t cpuset;
CPU_ZERO(&cpuset);
CPU_SET(thread_id, &cpuset);
pthread_setaffinity_np(pthread_self(), sizeof(cpu_set_t), &cpuset);
\end{code}
Это стабилизирует независимые счетчики тактов (\texttt{rdtsc}) для точного микросекундного профилирования и удерживает горячие фронты поиска в кэше L1/L2 конкретного ядра.

\subsection{Предотвращение ложного разделения кэш-линий (False Sharing)}
Поскольку рабочие потоки параллельно пишут статусы выполнения задач в свои структуры контекстов, попадание этих переменных в общую 64-байтную кэш-линию вызывает постоянную инвалидацию L1-кэша соседних ядер (Cache Line Ping-Pong). Для изоляции управляющих структур применено принудительное выравнивание:
\begin{code}{code:false-sharing}{C++}{Выравнивание и изоляция структуры ThreadContext}
struct alignas(64) ThreadContext {
    std::vector<NodeRecord> pq;      // Локальная 4-арная куча
    std::vector<uint32_t> dist;      // Локальные расстояния
    char padding[48];                // Гарантия изоляции границы
};
\end{code}

\section{Оптимизация приоритетной очереди}

Критическим узлом алгоритма поиска пути является операция извлечения минимума из очереди приоритетов. В рамках исследования была проведена эволюция структуры очереди:
\begin{equation*}
    \text{std::priority\_queue} \longrightarrow \text{Radix Queue} \longrightarrow \text{Strict 8-Ary SoA Heap}
\end{equation*}

Классическая двоичная куча (\texttt{std::priority\_queue}) имеет плохую локальность данных и большую высоту дерева $\log_2 N$. Внедрение 4-арной (и далее Strict SoA 8-арной) кучи позволило уменьшить высоту дерева в 2 раза и повысить коэффициент использования кэш-линий, так как 4 потомка (по 8 байт каждый) занимают ровно 32 байта и загружаются в процессор за один такт шины. Очистка очереди перед каждым поиском оптимизирована с $O(N)$ до $O(\text{size})$ путем ленивого сброса только посещенных узлов через стек истории.

\section{Низкоуровневая векторизация вычислений (AVX2)}

\subsection{Развертка активных маяков (Landmark Unrolling)}
Векторизация эвристики ALT выполняется на уровне AVX2 YMM-регистров. Из предрассчитанного набора маяков ( Landmark set) для каждого запроса МПР выбирает 4 наиболее активных (дающих наибольшую оценку в направлении цели). Чтение расстояний до маяков и вычисление безветвящейся метрики $\max(0, \Delta T)$ развернуто компилятором в 256-битные векторные инструкции (Loop Unrolling):
\begin{code}{code:loop-unrolling}{C++}{Развертка цикла без ветвлений для расчета эвристики ALT}
// Развернутый цикл без ветвлений в горячем контуре
for(int k = 0; k < 4; ++k) {
    uint32_t u_from = L_dist_from[v][active_L_idx[k]];
    uint32_t u_to   = L_dist_to[v][active_L_idx[k]];
    
    uint32_t h1 = (target_from[k] > u_from) ? (target_from[k] - u_from) : 0;
    uint32_t h2 = (u_to > target_to[k]) ? (u_to - target_to[k]) : 0;
    
    h_val = std::max({h_val, h1, h2});
}
\end{code}

\subsection{Векторизованный спуск 4-арной кучи (Sift-Down AVX2)}
Для исключения ветвлений при поиске минимального потомка в 4-арной куче применен векторный интринсик-спуск. Четыре дочерних узла \texttt{NodeRecord} (вес + ID, по 8 байт) загружаются в YMM регистр, после чего минимум находится с помощью параллельного Tree Reduction:
\begin{code}{code:avx2-sift-down}{C++}{Векторизованный спуск 4-арной кучи через интринсики AVX2}
inline uint32_t find_min_child_avx2(const uint32_t* children) {
    __m256i data = _mm256_loadu_si256((const __m256i*)children);
    __m256i id_mask_or = _mm256_set_epi32(
        0xFFFFFFFF, 0, 0xFFFFFFFF, 0, 0xFFFFFFFF, 0, 0xFFFFFFFF, 0
    );
    __m256i masked_for_min = _mm256_or_si256(data, id_mask_or);
    
    __m256i shuf1 = _mm256_permute2x128_si256(masked_for_min, masked_for_min, 0x01);
    __m256i min1  = _mm256_min_epu32(masked_for_min, shuf1);
    
    __m256i shuf2 = _mm256_shuffle_epi32(min1, _MM_SHUFFLE(0, 0, 0, 2));
    __m256i min2  = _mm256_min_epu32(min1, shuf2);
    
    uint32_t min_weight = (uint32_t)_mm256_extract_epi32(min2, 0);
    __m256i min_broadcast = _mm256_set1_epi32(min_weight);
    
    __m256i id_mask_and = _mm256_set_epi32(
        0, 0xFFFFFFFF, 0, 0xFFFFFFFF, 0, 0xFFFFFFFF, 0, 0xFFFFFFFF
    );
    __m256i weights_only = _mm256_and_si256(data, id_mask_and);
    __m256i cmp = _mm256_cmpeq_epi32(weights_only, min_broadcast);
    uint32_t bitmask = (uint32_t)_mm256_movemask_epi8(cmp);
    
    int child_idx = __builtin_ctz(bitmask) / 8;
    return children[child_idx * 2 + 1];
}
\end{code}
Данный подход полностью устраняет предсказание переходов (Branch Misprediction) процессора в фазе спуска кучи, экономя до 30 тактов на каждом шаге раскрытия узла.

\section{Интеграционный стек: Сеть, API и Пользовательский интерфейс}

Вычислительное ядро интегрировано в распределенную сервис-ориентированную инфраструктуру (Рисунок \ref{fig:network_arch}):
\begin{itemize}
    \item \textbf{Сетевой транспорт (ZeroMQ):} Для высокопроизводительного межпроцессного обмена (IPC) между C++ симулятором и внешним REST API используется шина ZeroMQ (библиотека \texttt{cppzmq}) с шаблоном Pub-Sub для потока метрик и Req-Rep для команд перестроения.
    \item \textbf{REST API Gateway (FastAPI):} Обеспечивает веб-интерфейс доступа к системе, асинхронно транслируя JSON-запросы от клиентов в бинарный протокол Protobuf/MessagePack для ZMQ-шины.
    \item \textbf{Графический клиент (PyQt5 + WebEngine):} Desktop-приложение, интегрирующее встраиваемый браузер Chrome для отображения векторной карты MapLibre GL. Визуализация плотности потока в реальном времени обеспечивается потоковой передачей тепловой карты (Heatmap) через WebSocket непосредственно из FastAPI.
\end{itemize}

\section{Выводы по второй главе}
Программно-аппаратная реализация навигационной системы на С++20 с использованием Data-Oriented Design и интринсиков AVX2 позволила вплотную приблизиться к физическому пределу пропускной способности архитектуры Zen 3. Привязка потоков (CPU Pinning), выравнивание структур по кэш-линиям (\texttt{alignas(64)}) и векторизованный обход 4-арной кучи гарантируют высочайшую стабильность времени поиска ($\approx 0.95$ мс на маршрут) и полную изоляцию от сетевых накладных расходов благодаря асинхронной интеграционной шине ZeroMQ/FastAPI.
