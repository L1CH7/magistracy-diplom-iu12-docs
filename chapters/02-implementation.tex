\section{Технологический стек и обоснование выбора компонентов}
\label{sec:tech_stack}

Для физической реализации спроектированной базы геоданных выбран стек технологий, ориентированный на высокую надежность, производительность пространственных операций и поддержку стандартных сетевых протоколов:
\begin{itemize}
    \item СУБД PostgreSQL~17~-- свободная объектно-реляционная система управления базами данных, предоставляющая развитые механизмы потоковой физической репликации на основе журнала упреждающей записи WAL, поддержку параллельного выполнения аналитических запросов и развитую систему транзакционного управления~\cite{postgrespro_mvcc_intro, postolenko2025_complexities};
    \item геопространственное расширение PostGIS~3.5~-- промышленный стандарт обработки пространственной информации, расширяющий ядро СУБД поддержкой геометрических типов данных стандарта OGC, индексами обобщенного поискового дерева GiST и набором функций динамической генерации векторных картографических тайлов MVT~\cite{lyashenko2019postgis, percona2025postgis};
    \item расширение графового анализа pgRouting~3.8~-- специализированная библиотека для выполнения сетевого анализа внутри СУБД, предоставляющая оптимизированные алгоритмы поиска кратчайших путей и анализа топологической связности ориентированных графов~\cite{basargin2021pgrouting, pgrouting2023advantages};
    \item модуль импорта картографических данных osm\_pbf\_import (на базе C++ библиотеки pyosmium)~-- оптимизированный инструмент пакетной загрузки картографических выгрузок OpenStreetMap, выполняющий первичную фильтрацию и заполнение пространственных таблиц;
    \item клиентский слой взаимодействия libpqxx / asyncpg~-- библиотеки доступа к базе данных по бинарному протоколу PostgreSQL, минимизирующие накладные расходы на преобразование типов данных при потоковой выгрузке графовых структур~\cite{habr2016asyncpg}.
\end{itemize}

\section{Разработка DDL-скриптов создания объектов базы данных}
\label{sec:ddl_scripts}

В соответствии со спроектированной моделью IDEF1X в базе данных формируются две изолированные схемы данных: схема исходных картографических слоев \texttt{osm} и схема графовых структур \texttt{graphs}.

\subsection{Создание схем данных и таблиц исходного слоя OSM}

Для обеспечения модульности и разделения прав доступа создание объектов начинается с инициализации схем и подключения пространственных расширений:
\begin{lstlisting}[language=SQL, caption={Инициализация расширений и таблиц схемы \texttt{osm}}]
CREATE EXTENSION IF NOT EXISTS postgis;
CREATE EXTENSION IF NOT EXISTS postgis_topology;
CREATE EXTENSION IF NOT EXISTS pgrouting;

CREATE SCHEMA IF NOT EXISTS osm;
CREATE SCHEMA IF NOT EXISTS graphs;

CREATE TABLE osm.ways (
    osm_id BIGINT PRIMARY KEY,
    highway VARCHAR(32) NOT NULL,
    name VARCHAR(256),
    oneway SMALLINT DEFAULT 0,
    maxspeed SMALLINT DEFAULT 60 CHECK (maxspeed > 0),
    lanes SMALLINT DEFAULT 1 CHECK (lanes > 0),
    z_layer SMALLINT DEFAULT 0 CHECK (z_layer BETWEEN -5 AND 5),
    geom_4326 GEOMETRY(LineString, 4326) NOT NULL,
    geom_3857 GEOMETRY(LineString, 3857) NOT NULL
);

CREATE TABLE osm.turn_restrictions (
    id BIGSERIAL PRIMARY KEY,
    from_way_id BIGINT NOT NULL REFERENCES osm.ways(osm_id) ON DELETE CASCADE,
    to_way_id BIGINT NOT NULL REFERENCES osm.ways(osm_id) ON DELETE CASCADE,
    via_node_id BIGINT NOT NULL,
    restriction_type VARCHAR(32) NOT NULL
);
\end{lstlisting}

В практической реализации импорта исходные картографические отношения маневров OpenStreetMap (содержащие разнородные теги и списки участников переменной длины) первично аккумулируются в буферной таблице с атрибутами \texttt{members} и \texttt{tags} типа JSONB. Далее в конвейере построения топологии (модуль \texttt{schema.hpp}) данные отношения разворачиваются и нормализуются с помощью оператора \texttt{CROSS JOIN LATERAL jsonb\_array\_elements} в каноническую реляционную структуру (листинг 2.1) со строгими ограничениями внешних ключей \texttt{from\_way\_id}, \texttt{to\_way\_id} и \texttt{via\_node\_id}, строго удовлетворяющую требованиям 3НФ.

\subsection{Создание таблиц топологического и реберного графов}

Схема \texttt{graphs} включает таблицы вершин и элементарных звеньев первичного графа, а также сущности реберно-вершинного графа допустимых маневров:
\begin{lstlisting}[language=SQL, caption={Создание таблиц схемы \texttt{graphs}}]
CREATE TABLE graphs.nodes (
    node_id BIGSERIAL PRIMARY KEY,
    osm_node_id BIGINT,
    geom GEOMETRY(Point, 4326) NOT NULL
);

CREATE TABLE graphs.edges (
    edge_id BIGSERIAL PRIMARY KEY,
    source_osm_id BIGINT NOT NULL REFERENCES osm.ways(osm_id) ON DELETE CASCADE,
    source_node_id BIGINT NOT NULL REFERENCES graphs.nodes(node_id) ON DELETE CASCADE,
    target_node_id BIGINT NOT NULL REFERENCES graphs.nodes(node_id) ON DELETE CASCADE,
    length_m DOUBLE PRECISION NOT NULL CHECK (length_m > 0),
    speed_limit SMALLINT NOT NULL CHECK (speed_limit > 0),
    is_isolated BOOLEAN DEFAULT FALSE,
    geom GEOMETRY(LineString, 4326) NOT NULL
);

CREATE TABLE graphs.eb_nodes (
    eb_node_id BIGINT PRIMARY KEY REFERENCES graphs.edges(edge_id) ON DELETE CASCADE,
    azimuth_out DOUBLE PRECISION NOT NULL,
    geom GEOMETRY(Point, 4326) NOT NULL
);

CREATE TABLE graphs.eb_edges (
    from_eb_node_id BIGINT NOT NULL REFERENCES graphs.eb_nodes(eb_node_id) ON DELETE CASCADE,
    to_eb_node_id BIGINT NOT NULL REFERENCES graphs.eb_nodes(eb_node_id) ON DELETE CASCADE,
    turn_angle DOUBLE PRECISION NOT NULL,
    turn_type SMALLINT NOT NULL,
    maneuver_time DOUBLE PRECISION NOT NULL CHECK (maneuver_time >= 0),
    PRIMARY KEY (from_eb_node_id, to_eb_node_id)
);
\end{lstlisting}

В программном модуле инициализации топологии C++ (\texttt{schema.hpp}) наименования столбцов графовых таблиц компактифицированы (\texttt{id}, \texttt{source\_id}, \texttt{target\_id}, \texttt{osm\_way\_id}), а в таблице \texttt{graphs.eb\_edges} первичным суррогатным ключом выступает \texttt{id BIGSERIAL} с уникальным ограничением на пару \texttt{(from\_eb\_node, to\_eb\_node)}, что обеспечивает идентичную семантику связей.

\subsection{Пространственные индексы GiST и триггер синхронизации проекций}

Для обеспечения высокой скорости выполнения пространственных предикатов и операций вырезки тайлов создаются специализированные индексы на основе обобщенного поискового дерева GiST (Generalized Search Tree)~\cite{nextgis2024indexes, gistda2017comparison}:
\begin{lstlisting}[language=SQL, caption={Создание пространственных индексов GiST}]
CREATE INDEX idx_osm_ways_geom_3857 ON osm.ways USING gist (geom_3857);
CREATE INDEX idx_osm_ways_geom_4326 ON osm.ways USING gist (geom_4326);
CREATE INDEX idx_graphs_edges_geom ON graphs.edges USING gist (geom);
CREATE INDEX idx_graphs_nodes_geom ON graphs.nodes USING gist (geom);
CREATE INDEX idx_graphs_edges_source_node ON graphs.edges (source_node_id);
CREATE INDEX idx_graphs_edges_target_node ON graphs.edges (target_node_id);
\end{lstlisting}

Использование индекса GiST на столбце \texttt{geom\_3857} сокращает время выполнения пространственных фильтраций в запросах генерации тайлов MVT с сотен миллисекунд до единиц миллисекунд благодаря быстрому отсечению непересекающихся ограничивающих прямоугольников (Bounding Box)~\cite{crunchydata2026performance}.

Для поддержания целостности между системами координат EPSG:4326 и EPSG:3857 разработан триггер автоматической синхронизации геометрии:
\begin{lstlisting}[language=SQL, caption={Триггер синхронизации проекции Меркатора}]
CREATE OR REPLACE FUNCTION osm.sync_geom_3857()
RETURNS TRIGGER AS $$
BEGIN
    NEW.geom_3857 := ST_Transform(NEW.geom_4326, 3857);
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_sync_geom_3857
BEFORE INSERT OR UPDATE OF geom_4326 ON osm.ways
FOR EACH ROW
EXECUTE FUNCTION osm.sync_geom_3857();
\end{lstlisting}

\section{Реализация пространственного конвейера подготовки данных}
\label{sec:spatial_pipeline}

\subsection{Топологическое нодирование с учетом высотных уровней и Grid Noding}

Первым этапом конвейера является пространственное нодирование дорожной сети, при котором полилинии дорог разрезаются во всех точках геометрических пересечений. При обработке масштабов крупной городской агломерации ($160\,689$ исходных участков) монолитное выполнение процедуры \texttt{ST\_Node} на всем массиве данных способно вызвать исчерпание оперативной памяти или чрезмерные задержки.

В связи с этим в конвейере реализована схема параллельного тайлового нодирования (Grid Noding): пространственный охват разбивается регулярной сеткой тайлов (размерностью $14 \times 12$), после чего пул вычислительных потоков параллельно выполняет нодирование геометрий внутри каждого тайла с буферным расширением \texttt{ST\_Expand(0.001)} для бесшовного сшивания на границах. Базовый декларативный запрос нодирования выполняется строго с группировкой по атрибуту высотного уровня \texttt{z\_layer}, благодаря чему исключаются ложные пересечения на многоуровневых эстакадах:

\begin{lstlisting}[language=SQL, caption={Запрос пространственного нодирования дорожной сети}]
WITH noded_lines AS (
    SELECT 
        w.z_layer,
        (ST_Dump(ST_Node(ST_Collect(ST_SnapToGrid(w.geom_4326, 0.000001))))).geom AS geom
    FROM osm.ways w
    GROUP BY w.z_layer
),
inserted_nodes AS (
    INSERT INTO graphs.nodes (geom)
    SELECT DISTINCT ST_StartPoint(geom) FROM noded_lines
    UNION
    SELECT DISTINCT ST_EndPoint(geom) FROM noded_lines
    ON CONFLICT DO NOTHING
    RETURNING node_id, geom
)
INSERT INTO graphs.edges (source_osm_id, source_node_id, target_node_id, length_m, speed_limit, geom)
SELECT 
    w.osm_id,
    sn.node_id AS source_node_id,
    tn.node_id AS target_node_id,
    ST_Length(nl.geom::geography) AS length_m,
    w.maxspeed,
    nl.geom
FROM noded_lines nl
JOIN osm.ways w ON ST_CoveredBy(nl.geom, w.geom_4326) AND w.z_layer = nl.z_layer
JOIN graphs.nodes sn ON ST_DWithin(ST_StartPoint(nl.geom), sn.geom, 0.00001)
JOIN graphs.nodes tn ON ST_DWithin(ST_EndPoint(nl.geom), tn.geom, 0.00001);
\end{lstlisting}

\subsection{Анализ связности графа и устранение изолированных компонент}

В дорожных сетях часто присутствуют изолированные фрагменты (парковки без выездов, изолированные дворовые проезды), попадание на которые приводит к зависанию навигационных алгоритмов. Для их выявления применяется функция \texttt{pgr\_strongComponents}, реализующая линейный алгоритм Тарьяна $O(V+E)$~\cite{tarjan2020algorithm, youcademy2024tarjan}:

\begin{lstlisting}[language=SQL, caption={Выявление и изоляция несвязных компонент по алгоритму Тарьяна}]
WITH scc_analysis AS (
    SELECT 
        node, 
        component
    FROM pgr_strongComponents(
        'SELECT edge_id AS id, source_node_id AS source, target_node_id AS target, 1.0 AS cost FROM graphs.edges'
    )
),
largest_component AS (
    -- Определение идентификатора наибольшей связной компоненты (LCC)
    SELECT component
    FROM scc_analysis
    GROUP BY component
    ORDER BY count(*) DESC
    LIMIT 1
)
-- Пометка изолированных ребер, не входящих в основную связную сеть
UPDATE graphs.edges e
SET is_isolated = TRUE
FROM scc_analysis scc, largest_component lc
WHERE e.source_node_id = scc.node AND scc.component <> lc.component;
\end{lstlisting}

\subsection{Построение ориентированного графа маневров с вычислением азимутов}

Для учета штрафов за повороты и запретов маневров ребра \texttt{graphs.edges} инвертируются в узлы \texttt{graphs.eb\_nodes}, а связующие маневры на перекрестках формируют ребра \texttt{graphs.eb\_edges}. Запрос рассчитывает углы поворота и отсекает запрещенные маневры:

\begin{lstlisting}[language=SQL, caption={Генерация реберно-вершинного графа маневров}]
-- Заполнение вершин реберного графа
INSERT INTO graphs.eb_nodes (eb_node_id, azimuth_out, geom)
SELECT 
    edge_id,
    ST_Azimuth(ST_PointN(geom, ST_NPoints(geom) - 1), ST_EndPoint(geom)),
    ST_EndPoint(geom)
FROM graphs.edges
WHERE is_isolated = FALSE;

-- Формирование ребер допустимых маневров с фильтрацией запретов
INSERT INTO graphs.eb_edges (from_eb_node_id, to_eb_node_id, turn_angle, turn_type, maneuver_time)
SELECT 
    e1.edge_id AS from_eb_node_id,
    e2.edge_id AS to_eb_node_id,
    -- Расчет относительного угла поворота от 0 до 360 градусов
    degrees(ST_Azimuth(ST_PointN(e2.geom, 1), ST_PointN(e2.geom, 2)) - eb1.azimuth_out + 2 * pi()) % 360 AS turn_angle,
    CASE 
        WHEN abs(degrees(ST_Azimuth(ST_PointN(e2.geom, 1), ST_PointN(e2.geom, 2)) - eb1.azimuth_out)) < 20 THEN 1 -- Прямо
        WHEN degrees(ST_Azimuth(ST_PointN(e2.geom, 1), ST_PointN(e2.geom, 2)) - eb1.azimuth_out) > 0 THEN 2        -- Направо
        ELSE 3                                                                                                     -- Налево
    END AS turn_type,
    CASE 
        WHEN abs(degrees(ST_Azimuth(ST_PointN(e2.geom, 1), ST_PointN(e2.geom, 2)) - eb1.azimuth_out)) < 20 THEN 0.5
        ELSE 3.5 -- Штраф 3.5 секунды за маневр с пересечением траекторий
    END AS maneuver_time
FROM graphs.edges e1
JOIN graphs.eb_nodes eb1 ON e1.edge_id = eb1.eb_node_id
JOIN graphs.edges e2 ON e1.target_node_id = e2.source_node_id AND e2.is_isolated = FALSE
-- Левое соединение с ограничениями поворотов для их исключения
LEFT JOIN osm.turn_restrictions tr ON tr.from_way_id = e1.source_osm_id 
                                  AND tr.to_way_id = e2.source_osm_id 
                                  AND tr.restriction_type LIKE 'no_%'
WHERE tr.id IS NULL;
\end{lstlisting}

\subsection{Динамическая генерация векторных тайлов MVT}

Отдача картографических слоев на ведомом узле выполняется единым декларативным SQL-запросом в рамках сервиса \texttt{data-processor} (эндпоинт \texttt{/api/v1/tiles/\{z\}/\{x\}/\{y\}.mvt}). Процедура трансформирует геометрию дорог в экранные координаты тайла и сериализует результат в двоичный формат Protobuf с фильтрацией классов дорог (LOD) в зависимости от масштаба~\cite{postgis_asmvt, kuvshinov2025mvt}:

\begin{lstlisting}[language=SQL, caption={Запрос динамической упаковки тайлов MVT}]
SELECT ST_AsMVT(tile_data.*, 'ways', 4096, 'geom') AS mvt_tile
FROM (
    SELECT 
        w.osm_id,
        w.highway,
        w.name,
        w.maxspeed,
        ST_AsMVTGeom(
            w.geom_3857,
            ST_TileEnvelope(:z, :x, :y),
            4096,
            256,
            true
        ) AS geom
    FROM osm.ways w
    WHERE w.geom_3857 && ST_TileEnvelope(:z, :x, :y)
) AS tile_data
WHERE tile_data.geom IS NOT NULL;
\end{lstlisting}

\section{Потоковая сериализация графа и преодоление барьера ввода-вывода}
\label{sec:io_serialization}

Применение классического реляционного интерфейса SQL для поиска путей в реальном времени при высокой частоте запросов (десятки тысяч запросов в секунду) порождает проблему «стены памяти» (Memory Wall)~\cite{drepper2007memory, mutlu2020primer}:
\begin{itemize}
    \item накладные расходы на разбор SQL-запросов и построение плана выполнения;
    \item постоянные блокировки в диспетчере транзакций MVCC при конкуренции за строки;
    \item задержки преобразования внутренних типов данных PostgreSQL в текстовые или сетевые форматы;
    \item массовые промахи процессорного кэша при обходе графа, распределенного по страницам буферного пула.
\end{itemize}

Для преодоления данного ограничения в комплексе реализован механизм потоковой бинарной сериализации сформированной топологии из PostgreSQL. Выгрузка осуществляется через модуль сборщика графа \texttt{graph\_builder} с использованием интерфейса \texttt{libpqxx}:
\begin{lstlisting}[language=SQL, caption={Потоковая выгрузка реберного графа из СУБД}]
SELECT 
    from_eb_node_id, 
    to_eb_node_id, 
    turn_angle, 
    maneuver_time 
FROM graphs.eb_edges 
ORDER BY from_eb_node_id;
\end{lstlisting}

После считывания вершин и ребер графа маневров в оперативную память C++ модуль \texttt{BinaryDumper} выполняет следующие ключевые оптимизации:
\begin{enumerate}
    \item Пространственная сортировка по Z-кривой Мортона (Morton Code): координаты геометрических центров дорожных сегментов преобразуются в одномерный код Мортона с последующей сортировкой узлов. Это гарантирует, что геометрически смежные участки дорог размещаются в смежных линиях кэш-памяти процессора (CPU cache-line locality), многократно снижая промахи L1/L2 кэша при обходе графа~\cite{drepper2007memory}.
    \item Перенумерация идентификаторов: узлам графа присваиваются плотные последовательные индексы $0 \dots |V|-1$.
    \item Расчет физических кинематических штрафов: на основе центростремительного ускорения $\sqrt{\mu g R}$ (где $\mu = 0.7$~-- коэффициент сцепления) и радиуса кривизны $R$ рассчитываются динамические скорости прохождения дуги поворота, внедряемые в статические веса переходов.
    \item Формирование плоских бинарных структур CSR (Compressed Sparse Row): топология графа упаковывается в массивы смещений указателей строк \texttt{row\_offsets} размерности $|V|+1$, массив целевых сегментов \texttt{col\_indices} размерности $|E|$ и массив статических весов времени \texttt{weights} размерности $|E|$.
\end{enumerate}

Сформированные массивы сохраняются в двоичные файлы \texttt{csr.bin}, \texttt{csr\_rev.bin}, \texttt{landmarks.bin} и \texttt{spatial\_grid.bin}.

Вычислительное ядро симуляции Traffic Core загружает бинарные файлы топологии через системный вызов ядра операционной системы POSIX \texttt{mmap}:
\begin{lstlisting}[language=C++, caption={Проецирование бинарного графа в память симулятора}]
int fd = open("csr.bin", O_RDONLY);
struct stat sb;
fstat(fd, &sb);

// Отображение файла топологии напрямую в виртуальную память процесса
void* addr = mmap(nullptr, sb.st_size, PROT_READ, MAP_PRIVATE | MAP_POPULATE, fd, 0);
madvise(addr, sb.st_size, MADV_WILLNEED);

auto* header = static_cast<TopologyHeader*>(addr);
const uint32_t* row_offsets = reinterpret_cast<const uint32_t*>((char*)addr + header->offsets_shift);
const uint32_t* col_indices = reinterpret_cast<const uint32_t*>((char*)addr + header->indices_shift);
\end{lstlisting}

Директива \texttt{MAP\_POPULATE} и системный вызов \texttt{madvise(MADV\_WILLNEED)} принудительно выполняют предварительную загрузку страниц в физическую память, устраняя прерывания по отсутствию страницы (\texttt{page faults}) во время моделирования. В результате поиск путей в ядре выполняется с задержкой 1--3 микросекунды без какого-либо обращения к СУБД в горячем цикле.

\section{Конфигурация и развертывание распределенного кластера СУБД}
\label{sec:cluster_deployment}

Развертывание распределенной базы данных выполнено в изолированных контейнерах с использованием системы оркестрации Docker Compose.

\subsection{Конфигурация ведущего узла (Master)}

На ведущем узле настраивается уровень генерации WAL-записей для поддержки физической репликации и выделяются пулы памяти для ELT-обработки:
\begin{lstlisting}[caption={Параметры \texttt{postgresql.conf} узла Master}]
wal_level = replica
max_wal_senders = 10
max_replication_slots = 5
hot_standby = on
shared_buffers = 4GB
work_mem = 64MB
maintenance_work_mem = 1GB
checkpoint_completion_target = 0.9
max_parallel_workers_per_gather = 4
\end{lstlisting}

На ведущем узле создается служебная учетная запись репликации:
\begin{lstlisting}[language=SQL, caption={Создание роли репликации}]
CREATE ROLE replicator WITH REPLICATION LOGIN ENCRYPTED PASSWORD 'ReplicaSecurePass2026';
\end{lstlisting}

\subsection{Конфигурация ведомого узла (Replica) и использование tmpfs}

Ведомый узел запускается в режиме \texttt{Hot Standby} и принимает поток WAL от ведущего узла. В файле конфигурации реплики активируется подключение:
\begin{lstlisting}[caption={Параметры подключения реплики}]
primary_conninfo = 'host=postgis-master port=5432 user=replicator password=ReplicaSecurePass2026 application_name=postgis_replica'
hot_standby = on
hot_standby_feedback = on
\end{lstlisting}

Для обеспечения максимальной скорости генерации и кэширования векторных тайлов MVT на реплике директория кэша монтируется в оперативную память через виртуальную файловую систему \texttt{tmpfs}:
\begin{lstlisting}[language=bash, caption={Монтирование каталога буферов MVT в память}]
mount -t tmpfs -o size=2G,noatime,nodiratime tmpfs /var/cache/mvt
\end{lstlisting}

\subsection{Спецификация Docker Compose}

Оркестрация распределенного кластера описывается файлом манифеста, представленным в листинге:
\begin{lstlisting}[caption={Манифест \texttt{docker-compose.yml} распределенного кластера}]
version: '3.8'

networks:
  rdb-network:
    driver: bridge

services:
  postgis-master:
    image: postgis/postgis:17-3.5
    container_name: postgis-master
    environment:
      POSTGRES_DB: transport_db
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: MasterSuperPassword
    volumes:
      - master_data:/var/lib/postgresql/data
      - ./init-scripts:/docker-entrypoint-initdb.d
    ports:
      - "5432:5432"
    networks:
      - rdb-network

  postgis-replica:
    image: postgis/postgis:17-3.5
    container_name: postgis-replica
    environment:
      PGUSER: replicator
      PGPASSWORD: ReplicaSecurePass2026
    volumes:
      - replica_data:/var/lib/postgresql/data
    tmpfs:
      - /var/cache/mvt:size=2G,mode=1777
    ports:
      - "5433:5432"
    depends_on:
      - postgis-master
    networks:
      - rdb-network

volumes:
  master_data:
  replica_data:
\end{lstlisting}

В рамках архитектуры комплекса предусмотрена поддержка двух эксплуатационных профилей:
\begin{itemize}
    \item профиль локальной разработки и отладки вычислительного ядра: задействует одиночный контейнер СУБД \texttt{postgis}, что снижает потребление оперативной памяти на рабочей станции исследователя;
    \item профиль промышленной эксплуатации и нагрузочного тестирования: развертывает распределенный кластер Master-Replica согласно спецификации листинга. Данная топология обеспечивает физическую изоляцию тяжелых пакетных задач построения топологии на ведущем узле от параллельных запросов картографической визуализации MVT на ведомом узле.
\end{itemize}
