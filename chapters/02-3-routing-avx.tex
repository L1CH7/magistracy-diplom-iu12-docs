\section{Алгоритмическая реализация динамического поиска путей и векторные оптимизации}

Сердцем вычислительного ядра является класс маршрутизатора, реализующий алгоритм поиска кратчайшего пути с временной зависимостью. Для обеспечения заявленной пропускной способности в тысячи запросов в секунду код маршрутизатора глубоко оптимизирован с использованием векторных инструкций процессора.

При поиске кратчайшего пути основным узким местом выступает извлечение узла с минимальным весом из очереди приоритетов. Традиционная двоичная куча создает логарифмическую глубину дерева, что замедляет работу.

Разработанное ядро использует векторизованную 8-арную кучу в формате структуры массивов SoA в качестве основной очереди приоритетов. Внедрение 8-арной кучи уменьшает глубину дерева в три раза по сравнению с классической двоичной кучей, что снижает количество промахов кэша процессора при обходе уровней \cite{outerloop_heap}. Однако высокая арность требует поиска минимума среди всех восьми потомков узла на каждом уровне, увеличивая количество сравнений и условных переходов.

Для нивелирования этих затрат в проекте реализован поиск минимального потомка в 8-арной куче с использованием 256-битных векторных инструкций AVX2 \cite{kusswurm2014modern, fog_optimizing_cpp}. Восемь 32-битных весов потомков загружаются в один векторный регистр. Благодаря выравниванию массивов по границе 64 байт применяется инструкция выровненного чтения, а поддержка инварианта бесконечного веса для пустых элементов за границей размера кучи устраняет надобность в динамическом маскировании на лету. Поиск минимального значения осуществляется за счет каскада векторных минимумов и перестановок, исключающих ветвление процессора:

\begin{plaincode}{find_min_child_avx2}{Поиск минимального потомка в 8-арной SoA-куче с совместным кодированием ключа и индекса}
// Загрузка упакованных весов 8 потомков (вес сдвинут на 3 бита влево, 
// младшие 3 бита кодируют относительный индекс 0..7)
const __m256i* p_child = reinterpret_cast<const __m256i*>(&weights_[first]);
__m256i v = _mm256_loadu_si256(p_child);

// Горизонтальный поиск минимума с помощью инструкций _mm256_min_epu32
__m256i p1 = _mm256_permute2x128_si256(v, v, 1);
__m256i m1 = _mm256_min_epu32(v, p1);
__m256i m2 = _mm256_min_epu32(m1, _mm256_shuffle_epi32(m1, _MM_SHUFFLE(1, 0, 3, 2)));
__m256i m3 = _mm256_min_epu32(m2, _mm256_shuffle_epi32(m2, _MM_SHUFFLE(2, 3, 0, 1)));
uint32_t min_combined = _mm256_extract_epi32(m3, 0);

// Декодирование веса и относительного индекса за 0 тактов процессора
uint32_t min_w = min_combined >> 3;
uint32_t local_idx = min_combined & 7;
uint32_t min_idx = first + local_idx;
\end{plaincode}

Традиционный поиск минимального узла в $d$-арных кучах вызывает частые ошибки предсказания ветвлений процессора (branch mispredictions) \cite{biggar_sorting}. Векторные инструкции AVX2 позволяют выполнять поиск без ветвлений. Однако стандартный SIMD-алгоритм с векторным сравнением (\texttt{\_mm256\_cmpeq\_epi32}), генерацией маски (\texttt{\_mm256\_movemask\_ps}) и подсчетом нулей (\texttt{\_\_builtin\_ctz}) создает длинную цепочку зависимостей по данным (data dependency chain), блокируя конвейер процессора при межрегистровом переносе \cite{fog_optimizing_cpp}.

Для устранения этой задержки в вычислительном ядре применено совместное кодирование ключа и индекса в единое 32-битное слово \cite{kusswurm2014modern}. Битовый сдвиг веса ребра влево освобождает младшие разряды под локальный индекс потомка. Векторная инструкция поиска минимума \texttt{\_mm256\_min\_epu32} автоматически сохраняет индекс минимального элемента в младших битах результата. Это позволяет извлечь позицию и вес за одну побитовую операцию без использования инструкций сравнения и маскирования. Отсутствие динамического маскирования на лету снижает общее количество инструкций в горячем цикле, повышая аппаратную скорость выполнения.

При раскрытии вершин алгоритм динамического поиска оценивает вес каждого маневра. Маршрутизатор считывает объемы трафика из временных интервалов без использования транзакционных мьютексов. Код обращается к массивам атомарных переменных со слабым порядком памяти \cite{cpp_p2055r1, cpp_p0668r5}. 

Для устранения ступенчатости штрафов реализован механизм линейной интерполяции времени, который считывает объемы из двух соседних 5-минутных слотов и интерполирует непосредственно квадраты плотности потока, применяя заранее вычисленный целочисленный коэффициент:
\begin{plaincode}{bpr_lerp_fixed_point}{Расчет задержки методом линейной интерполяции}
uint64_t scale = static_cast<uint64_t>(k_magic[v]);
uint64_t p1 = scale * v1 * v1;
uint64_t p2 = scale * v2 * v2;
uint32_t bpr_penalty = static_cast<uint32_t>(
    (p1 + ((p2 - p1) * local_sec) / 300) >> 20);
\end{plaincode}

После того как оптимальный путь найден, роутер осуществляет резервирование емкости. Проходя по восстановленному пути, для каждого сегмента вызывается операция атомарного сложения, которая инкрементирует значение в соответствующем временном интервале. Это математически аппроксимирует эффект перераспределения потока, уводя следующих агентов на альтернавые маршруты.

Для мгновенной реакции модуля принятия решений на дорожные инциденты разработан быстрый пространственный индекс. Классические пространственные деревья с указателями в куче заменены регулярной сеткой в непрерывном массиве памяти \cite{drepper2007memory}. 

Привязка географической геометрии дорог к ячейкам сетки выполняется на этапе предварительной обработки. В реальном времени модуль принятия решений формирует ограничивающую рамку зоны инцидента и за константное время получает доступ к списку идентификаторов ребер, попавших в ячейки. Затем модуль принятия решений выставляет директивные штрафы в атомарное поле штрафов целевых сегментов. Благодаря строгой архитектуре кэширования, поиск затронутых ребер и обновление штрафов происходят за доли микросекунды, не блокируя работу соседних потоков пула маршрутизатора.

Специализированный асинхронный протокол на базе бинарной сериализации минимизирует накладные расходы при обмене данными между клиентом на Python, сетевым шлюзом и вычислительным ядром C++. 

Жизненный цикл выполнения запроса на расчет маршрута состоит из следующих шагов:
\begin{enumerate}
    \item Инициализация запроса: клиентское приложение отправляет запрос с массивом географических точек на шлюз по протоколу HTTP методом POST.
    \item Сериализация: шлюз упаковывает параметры запроса в плоский бинарный буфер фиксированного формата, что исключает медленный парсинг JSON на стороне вычислительного ядра.
    \item Сетевой транспорт: шлюз отправляет бинарный буфер в фоновый поток вычислительного ядра через сокет ZeroMQ REQ.
    \item Пространственная привязка: вычислительный поток принимает сообщение и привязывает координаты старта и финиша к ближайшим ребрам графа через плоский пространственный индекс за константное время.
    \item Поиск пути: маршрутизатор ищет кратчайший путь на компактном графе. При релаксации ребер алгоритм рассчитывает динамический вес сегментов с учетом ожидаемого времени прибытия, а менеджер объемов интерполирует плотность по 5-минутным корзинам.
    \item Формирование ответа: ядро упаковывает результаты в многочастное сообщение ZeroMQ для исключения лишнего копирования памяти и возвращает шлюзу по сокету REP.
    \item Отрисовка: шлюз распаковывает бинарные фреймы, преобразует геометрию в формат GeoJSON и возвращает её клиенту в теле HTTP-ответа для визуализации на карте.


\end{enumerate}
