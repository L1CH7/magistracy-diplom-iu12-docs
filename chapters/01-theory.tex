\section{Анализ предметной области и требования к системе}
\label{sec:domain_analysis}

Проектирование высокопроизводительных навигационных систем и комплексов имитационного моделирования транспортных потоков базируется на адекватном представлении геопространственной структуры улично-дорожной сети (УДС). В отличие от классических учетных систем, база геоданных навигационного назначения оперирует сложными геометрическими объектами, топологическими связями и многоуровневыми правилами маневрирования~\cite{lyashenko2019postgis, basargin2021pgrouting}.

Основным источником открытых данных о дорожной инфраструктуре является проект OpenStreetMap (OSM). Геометрия дорог в OSM представляется в виде цепочек географических координат (полилиний), снабженных набором атрибутивных тегов. Однако исходные данные OSM обладают рядом особенностей, препятствующих их непосредственному использованию в навигационных расчетах:
\begin{itemize}
    \item отсутствие явной топологической планарности: пересекающиеся в пространстве дороги зачастую не имеют общей вершины в точке геометрического пересечения;
    \item разноуровневые развязки: мостовые переходы, эстакады и туннели пересекаются на карте в двумерной проекции, но физически не имеют съездов без специальных переходных рамп;
    \item раздельное хранение ограничений маневров: запреты левых поворотов, разворотов и предписания движения по полосам хранятся в отдельных сущностях отношений (relations), требующих связывания с линейными дорожными сегментами;
    \item наличие изолированных и тупиковых фрагментов: технологические съезды, внутридворовые проезды и ошибки разметки создают несвязные компоненты графа, попадание в которые приводит к сбою навигационных алгоритмов~\cite{tarjan2020algorithm}.
\end{itemize}

К проектируемой реляционной базе геоданных предъявляются следующие фундаментальные требования:
\begin{enumerate}
    \item Обеспечение целостности топологии: база данных должна выполнять автоматическое геометрическое нодирование с учетом высотных уровней и формировать ориентированный граф дорожного движения.
    \item Поддержка реберно-вершинной инверсии: для строгого учета штрафов за маневры и запретов поворотов структура данных должна представлять физические отрезки дорог в виде узлов вычислительного графа, а допустимые маневры на перекрестках~-- в виде ориентированных ребер.
    \item Нормализация структуры данных: реляционные таблицы должны находиться в третьей нормальной форме (3НФ), исключая дублирование атрибутов и аномалии обновления при редактировании картографического графа.
    \item Изоляция аналитической и клиентской нагрузки: тяжелые транзакционные процедуры пространственной обработки геометрий не должны блокировать клиентские запросы на визуализацию дорожной сети.
    \item Высокая скорость картографической отдачи: система должна поддерживать динамическую агрегацию слоев в бинарный формат векторных тайлов MVT (Mapbox Vector Tiles) без использования промежуточных дисковых кэшей.
\end{enumerate}

\section{Структура входных картографических данных}
\label{sec:input_data}

Входными данными для проектируемой базы данных служат картографические выгрузки формата OSM PBF (Protocolbuffer Binary Format), охватывающие заданный географический регион (например, городскую агломерацию г.~Казани или г.~Москвы). Географические координаты точек в исходном файле зафиксированы в эллипсоидальной системе координат WGS-84 (стандарт EPSG:4326) в виде широты и долготы в градусах.

Модель данных OSM оперирует тремя базовыми типами элементов:
\begin{itemize}
    \item точки (\texttt{nodes})~-- точечные объекты с координатами широты и долготы;
    \item линии (\texttt{ways})~-- упорядоченные последовательности идентификаторов точек, формирующие ломаные линии или замкнутые полигоны;
    \item отношения (\texttt{relations})~-- логические объединения точек, линий и других отношений, задающие сложные структуры, включая маршруты общественного транспорта и ограничения движения.
\end{itemize}

При импорте дорожного каркаса выполняется специализированная фильтрация по ключевому тегу \texttt{highway}. В базу данных отбираются категории дорог, предназначенные для автомобильного движения: \texttt{motorway}, \texttt{trunk}, \texttt{primary}, \texttt{secondary}, \texttt{tertiary}, \texttt{unclassified}, \texttt{residential}, а также соответствующие соединительные рампы (\texttt{*\_link}). Пешеходные дорожки (\texttt{footway}), велосипедные полосы (\texttt{cycleway}) и служебные просеки исключаются на этапе первичного разбора.

Особое значение имеют высотные характеристики участков дорог. В тегах OSM вертикальное разделение кодируется атрибутами \texttt{layer} (целочисленный уровень от $-5$ до $+5$), \texttt{bridge} (признак мостового сооружения) и \texttt{tunnel} (признак подземного туннеля). Для корректного нодирования пересечений в базе данных формируется производный атрибут \texttt{z\_layer}, равный значению тега \texttt{layer} при его наличии, либо $+1$ для мостов и $-1$ для туннелей по умолчанию.

Ограничения маневрирования на перекрестках описываются отношениями с тегом \texttt{type=restriction}. Такое отношение объединяет три роли:
\begin{enumerate}
    \item \texttt{from}~-- линия дорожного сегмента, с которого совершается маневр;
    \item \texttt{via}~-- промежуточная точка перекрестка или соединительная линия;
    \item \texttt{to}~-- линия дорожного сегмента, на который осуществляется выезд.
\end{enumerate}
Тег ограничения принимает значения безусловного запрета (\texttt{no\_left\_turn}, \texttt{no\_right\_turn}, \texttt{no\_u\_turn}, \texttt{no\_straight\_on}) либо обязательного предписания (\texttt{only\_right\_turn}, \texttt{only\_left\_turn}, \texttt{only\_straight\_on}).

Для обеспечения возможности отрисовки картографической подложки в веб-клиентах пространственные данные преобразуются из географической системы WGS-84 (EPSG:4326) в прямоугольную проекцию Меркатора на сфере Web Mercator (EPSG:3857), использующую метрические единицы измерения.

\section{Функциональное моделирование процессов обработки данных в стандарте IDEF0}
\label{sec:idef0_modeling}

Функциональное моделирование системы выполнено в соответствии с методологией структурного анализа и проектирования SADT и международным стандартом IDEF0. Модель отражает логику преобразования пространственной информации от исходного картографического файла до структур высокоскоростной навигации и картографических тайлов.

\subsection{Контекстная диаграмма процесса (уровень А-0)}

Контекстная диаграмма верхнего уровня А-0 отражает границы проектируемой системы в окружении внешних информационных потоков. Контекстная диаграмма представлена на рисунке~\ref{fig:idef0_a0}.

В соответствии с правилами нотации IDEF0 информационные и управляющие потоки классифицируются по четырем сторонам функционального блока (интерфейс ICOM):
\begin{itemize}
    \item входы (стрелки слева)~-- исходные данные, преобразуемые процессом: картографические выгрузки дорожной сети OSM (\texttt{.osm.pbf}), конфигурационный файл границ полигона охвата (\texttt{bboxes.yaml}), а также нормативные правила дорожного движения и скоростные ограничения;
    \item управление (стрелки сверху)~-- нормативные документы и стандарты, регламентирующие выполнение процесса: стандарты Open Geospatial Consortium (OGC Simple Features SQL), спецификация бинарного протокола векторных тайлов Mapbox Vector Tiles (MVT/Protobuf) и критерии топологической связности транспортных сетей;
    \item механизмы (стрелки снизу)~-- программные и аппаратные средства реализации: ведущий узел СУБД PostgreSQL~17 с расширением PostGIS (Master: пространственный конвейер ELT), ведомый узел СУБД (Read Replica: сервер генерации векторных тайлов MVT), консольная утилита импорта \texttt{osm2pgsql} и библиотека алгоритмов на графах pgRouting;
    \item выходы (стрелки справа)~-- результаты выполнения процесса: бинарные векторные картографические тайлы (MVT/Protobuf), топологический граф допустимых маневров и сериализованные бинарные снимки графа для навигационного ядра.
\end{itemize}

Главная архитектурная особенность контекстной диаграммы заключается в разделении исполнительных механизмов снизу: транзакционная и вычислительная нагрузка сборки топологии закреплена за ведущим узлом СУБД (Master), а генерация клиентских визуальных слоев MVT возложена на ведомый узел (Replica), что устраняет взаимное влияние разнородных потоков данных.

\subsection{Декомпозиция процесса первого уровня (блоки А1--А4)}

Диаграмма декомпозиции первого уровня детально раскрывает внутренние фазы преобразования геоданных и структуру промежуточных хранилищ. Диаграмма декомпозиции представлена на рисунке~\ref{fig:idef0_decomp}.

\begin{figure}[htbp]
    \centering
    \includesvg[width=\linewidth,inkscapelatex=false]{assets/svg/02-idef0.svg}
    \caption{Диаграмма декомпозиции IDEF0 (блоки А1--А4) конвейера пространственной обработки}
    \label{fig:idef0_decomp}
\end{figure}

Процесс декомпозирован на четыре последовательно-параллельных функциональных блока:
\begin{enumerate}
    \item Блок А1: «Импорт и первичная фильтрация геометрий OSM». Утилита \texttt{osm2pgsql} считывает сжатый бинарный файл OSM, отсекает неавтомобильные типы дорог и наполняет реляционную таблицу \texttt{osm.ways}, а также таблицу запретов \texttt{osm.turn\_restrictions}. Из таблицы \texttt{osm.ways} формируется прямой поток пространственных данных на механизм сервера тайлов MVT (ведомый узел), обеспечивая немедленную визуализацию дорожной сетки без ожидания построения графа маневров.
    \item Блок А2: «Пространственное нодирование и топологическая очистка». Выполняется пространственное разрезание полилиний дорог в точках их пересечений функциями PostGIS (\texttt{ST\_SnapToGrid}, \texttt{ST\_Node}). Разрезание осуществляется строго с группировкой по высотному уровню \texttt{z\_layer}, благодаря чему исключаются ложные пересечения на многоуровневых эстакадах. Результатом блока являются заполненные таблицы узлов \texttt{graphs.nodes} и элементарных ребер \texttt{graphs.edges}.
    \item Блок А3: «Анализ связности и устранение изолированных компонент». На основе таблиц \texttt{graphs.nodes} и \texttt{graphs.edges} запускается алгоритм Тарьяна выявления сильно связанных компонент ориентированного графа (\texttt{pgr\_strongComponents}). Выделяется наибольшая связанная компонента (LCC). Все изолированные карманы, тупики и некорректно оцифрованные сегменты получают признак изоляции и исключаются из дальнейшей обработки.
    \item Блок А4: «Генерация реберно-вершинного графа маневров». Производится инверсия графа: ребра \texttt{graphs.edges} преобразуются в узлы графа маневров \texttt{graphs.eb\_nodes}, а физические маневры на перекрестках становятся ребрами \texttt{graphs.eb\_edges}. Для каждого маневра вычисляются азимуты въезда и выезда (\texttt{ST\_Azimuth}), определяется угол поворота и выполняется фильтрация по таблице запретов \texttt{osm.turn\_restrictions}. Итоговая топология выгружается в бинарный снимок для навигационного ядра симуляции.
\end{enumerate}

\section{Инфологическая и даталогическая модель базы данных в стандарте IDEF1X}
\label{sec:idef1x_modeling}

Даталогическая модель базы данных разработана с учетом требований реляционной теории и стандарта IDEF1X. Схема физически разделена на две схемы данных СУБД: схему хранения исходных картографических объектов \texttt{osm} и схему графовых топологических структур \texttt{graphs}.

\subsection{Обоснование третьей нормальной формы (3НФ)}

Структура таблиц базы данных спроектирована с соблюдением требований нормализации:
\begin{itemize}
    \item Первая нормальная форма (1НФ): все атрибуты являются атомарными. Составные атрибуты тегов OSM распакованы в отдельные типизированные столбцы; геометрические объекты представлены неделимыми типами PostGIS (\texttt{geometry}). В таблицах отсутствуют повторяющиеся группы столбцов.
    \item Вторая нормальная форма (2НФ): все неключевые атрибуты функционально полно зависят от первичного ключа соответствующей таблицы. В таблицах с составными первичными ключами отсутствуют частичные функциональные зависимости от части ключа.
    \item Третья нормальная форма (3НФ): в структуре отсутствуют транзитивные функциональные зависимости неключевых атрибутов от первичного ключа. Все вычисляемые динамические показатели исключены из структуры постоянных таблиц.
\end{itemize}

Особое внимание уделено исключению динамических расчетных полей (таких как динамическая пропускная способность дороги $C_{300}$, текущая плотность потока или множитель задержки $K_{\text{magic}}$). Включение подобных параметров в реляционные таблицы привело бы к нарушению 3НФ, транзитивным зависимостям от времени суток и непрерывной блокировке строк транзакциями обновления. Данные показатели рассчитываются аналитически за пределами транзакционного контура.

Реляционная модель данных, включающая 6 нормализованных сущностей, представлена на рисунке~\ref{fig:idef1x_model}.

\begin{figure}[htbp]
    \centering
    \includesvg[width=\linewidth,inkscapelatex=false]{assets/svg/03-idef1x.svg}
    \caption{Даталогическая модель базы геоданных в нотации IDEF1X (3НФ)}

На диаграмме выделены следующие сущности:
\begin{enumerate}
    \item \texttt{OsmWays}~-- таблица исходных линий дорожной сети, импортированных из OSM. Первичный ключ~-- \texttt{osm\_id}. Содержит атрибуты класса дороги (\texttt{highway}), скоростного ограничения (\texttt{maxspeed}), признака одностороннего движения (\texttt{oneway}), высотного уровня (\texttt{z\_layer}) и пространственную геометрию в двух проекциях (\texttt{geom\_4326}, \texttt{geom\_3857}).
    \item \texttt{OsmTurnRestrictions}~-- таблица ограничений маневрирования. Первичный ключ~-- \texttt{id}. Связана с \texttt{OsmWays} неидентифицирующими связями «один-ко-многим» по внешним ключам \texttt{from\_way\_id} и \texttt{to\_way\_id}. Атрибут \texttt{via\_node\_id} определяет узел сочленения, а \texttt{restriction\_type}~-- тип правила.
    \item \texttt{GraphsNodes}~-- таблица топологических вершин базового графа после нодирования. Первичный ключ~-- \texttt{node\_id}. Хранит пространственные координаты перекрестка в виде точечной геометрии \texttt{geom}.
    \item \texttt{GraphsEdges}~-- таблица элементарных направленных звеньев сети. Первичный ключ~-- \texttt{edge\_id}. Содержит внешние ключи: ссылку на исходную линию \texttt{source\_osm\_id} (\texttt{OsmWays}), начальную вершину \texttt{source\_node\_id} и конечную вершину \texttt{target\_node\_id} (\texttt{GraphsNodes}). Связи поддерживают каскадное удаление (\texttt{ON DELETE CASCADE}).
    \item \texttt{GraphsEbNodes}~-- таблица вершин реберно-вершинного графа маневров. Первичный ключ~-- \texttt{eb\_node\_id}, связанный с \texttt{GraphsEdges.edge\_id} идентифицирующей связью «один-к-одному» ($1:1$). Атрибут \texttt{azimuth\_out} хранит исходный угол выезда с сегмента.
    \item \texttt{GraphsEbEdges}~-- таблица ребер графа маневров (допустимых переходов между сегментами). Первичный ключ составной~-- \texttt{(from\_eb\_node\_id, to\_eb\_node\_id)}. Содержит геометрический угол поворота \texttt{turn\_angle}, категорию маневра \texttt{turn\_type} и расчетное штрафное время проезда перекрестка \texttt{maneuver\_time}.
\end{enumerate}

\section{Архитектура распределенного комплекса хранения и обработки данных}
\label{sec:system_architecture}

В состав распределенной системы входят следующие ключевые узлы и службы:
\begin{itemize}
    \item Узел Master (ведущий узел СУБД): выделенный инстанс PostgreSQL~17 с установленными расширениями PostGIS и pgRouting. Узел сконфигурирован для высокопроизводительной пакетной обработки геоданных: увеличен размер рабочей памяти \texttt{work\_mem} и объем пула буферов \texttt{shared\_buffers}. Здесь выполняется импорт \texttt{osm2pgsql}, нодирование, алгоритм Тарьяна и формирование реберного графа. Все операции протоколируются в журнал упреждающей записи WAL.
    \item Узел Read Replica (ведомый узел СУБД): экземпляр PostgreSQL, находящийся в режиме непрерывного горячего резерва (\texttt{Hot Standby}). Синхронизируется с ведущим узлом по протоколу физической потоковой репликации WAL. Узел обслуживает запросы микросервиса тайлов MVT.
    \item Сервер векторных тайлов MVT: легковесный сервис, взаимодействующий с репликой по бинарному протоколу PostgreSQL. Сервер преобразует экранные координаты тайла $(z, x, y)$ в SQL-запросы вырезки геометрий по огибающему полигону (\texttt{ST\_TileEnvelope}) и формирует ответ в формате Protobuf. Для исключения дисковых задержек буферы генерации тайлов размещаются в виртуальной файловой системе в оперативной памяти (\texttt{tmpfs}).
    \item Вычислительное ядро симуляции Traffic Core: независимый сервис на языке C++20, выполняющий динамическое агент-ориентированное моделирование потоков. Ядро не взаимодействует с СУБД по сети в горячем цикле. Вместо этого при инициализации ядро считывает предрассчитанный бинарный снимок графа непосредственно в структуры CSR (Compressed Sparse Row) в оперативной памяти через системный вызов \texttt{mmap}.
    \item Клиентское приложение: диспетчерское рабочее место на базе Qt~6 и MapLibre Native, получающее бинарные векторные тайлы MVT от сервера тайлов по протоколу HTTP и отображающее динамическую дорожную обстановку.
\end{itemize}

Предложенная архитектура обеспечивает полное преодоление проблемы дискового ввода-вывода (I/O Bottleneck): ведущий узел свободен от сетевых запросов клиентской визуализации, а ведомый узел генерирует векторные тайлы исключительно из оперативной памяти без блокировок транзакций.
