\section{Архитектура программного ядра маршрутизации}

Разработанный программный комплекс представляет собой высокопроизводительный системный процесс (демон), написанный на стандарте C++20. В отличие от классических монолитных транспортных симуляторов, архитектура ядра маршрутизации базируется на принципе строгой изоляции вычислительных контуров и отказе от сильной связности модулей.

Функциональная декомпозиция модулей.
Для предотвращения усложнения кодовой базы и появления перегруженных классов, система физически разделена на изолированные статические библиотеки (модули). Каждый модуль имеет собственный конфигурационный файл сборщика и инкапсулирует свою зону ответственности:

\begin{itemize}
    \item «Маршрутизатор» — чистый вычислительный модуль без сохранения состояния, работающий в оперативной памяти. Он отвечает исключительно за алгоритмический обход графа (динамический поиск по опорным вершинам), поддержку 4-арных куч и работу с плоскими массивами компактного формата. Не содержит логики симуляции.
    \item «Поставщик данных симуляции» (Среда и Симулятор) — модуль, отвечающий за одномерную кинематику агентов (моделирование потока как сжимаемой жидкости), продвижение физического времени и трансляцию сырых параметров загруженности дорожной сети.
    \item «Модуль принятия решений» — интеллектуальный регулятор системы. Анализирует потоки данных от поставщика данных симуляции, выявляет зарождающиеся заторы с помощью пространственных индексов и отправляет асинхронные триггерные запросы в маршрутизатор для локального или глобального перестроения путей движения.
    \item «Базовые структуры» — слой инфраструктуры, предоставляющий пулы рабочих потоков, безблокировочные очереди сообщений и общую диспетчеризацию фоновых задач.
    \item «Системная служба» — точка входа в программу, реализующая паттерн точки композиции.
\end{itemize}

Инверсия управления и точка композиции зависимостей.
Связывание независимых подсистем осуществляется через паттерн внедрения зависимостей. Модули общаются исключительно через абстрактные контракты (например, интерфейсы поставщика данных симуляции или публикатора телеметрии), ничего не зная о внутренней реализации друг друга. 

Сборка итогового конвейера симуляции происходит в единственной точке приложения — главной функции сборки, выступающей в роли корня композиции зависимостей. Оркестратор инициализирует объекты в строгой последовательности от ядра к периферии, формируя следующий главный цикл:
\begin{enumerate}
    \item Шаг симуляции: модуль симуляции продвигает физику движения на фиксированный временной шаг и формирует массивы изменений.
    \item Шаг телеметрии: извлеченные легковесные дельты изменений передаются в сетевой транспортный слой для асинхронной отправки на веб-клиенты.
    \item Шаг аналитики: модуль принятия решений забирает сгенерированные симулятором события-оповещения (например, критическое отклонение ожидаемого времени прибытия).
    \item Шаг маршрутизации: модуль принятия решений запрашивает у пула потоков альтернативные маршруты и возвращает их агентам.
\end{enumerate}

Данный подход превращает архитектуру в легко расширяемый конструктор, позволяющий в будущем (например, при интеграции машинного обучения) прозрачно подменить математический модуль принятия решений на нейросетевой инференс без переписывания транспортного ядра.

Эффективное объектно-ориентированное проектирование и организация данных в памяти.
Классический объектно-ориентированный дизайн (с обильным использованием интерфейсов и виртуальных функций) провоцирует промахи кэша инструкций процессора и блокирует агрессивное встраивание кода компилятором на этапе компиляции. В горячем цикле маршрутизатора это приводит к недопустимому нарушению бюджета времени в 190 наносекунд на одну итерацию обхода узла.

Для сочетания чистой архитектуры с максимальной аппаратной скоростью выполнения применена парадигма абстракций с нулевой стоимостью выполнения:
\begin{enumerate}
    \item Запрет на виртуальные вызовы: в методах обхода графа и симуляции физики (основных методах продвижения физики и расчета маршрутов) полностью исключено динамическое связывание с использованием таблиц виртуальных функций.
    \item Инкапсуляция плоских данных: тяжелые массивы внутренних указателей строк и индексов столбцов компактного формата инкапсулируются внутри классов как приватные поля стандартного вектора. Внешний интерфейс предоставляет безопасные методы доступа, помеченные директивами компилятора для встраивания.
    \item Полиморфизм на этапе компиляции: компилятор полностью вырезает вызовы таких методов, заменяя их прямым ассемблерным смещением в оперативной памяти. Это гарантирует скорость выполнения на уровне языка ассемблера при сохранении строгой типизации и безопасности памяти современного C++.
\end{enumerate}
