\section{Архитектура программного ядра маршрутизации}

Разработанный программный комплекс представляет собой фоновую системную службу, разработанную в соответствии со стандартом C++20 \cite{iso_iec_14882_2020}. В отличие от классических монолитных транспортных симуляторов, архитектура ядра маршрутизации базируется на принципе строгой изоляции вычислительных контуров и отказе от сильной связности модулей \cite{butorin2026thread}.

Функциональная декомпозиция модулей.
Для предотвращения усложнения кодовой базы и появления перегруженных классов, система физически разделена на изолированные статические библиотеки (модули). Каждый модуль имеет собственный конфигурационный файл сборщика и инкапсулирует свою зону ответственности:

\begin{itemize}
    \item «Маршрутизатор»~-- чистый вычислительный модуль без сохранения состояния. Его ключевая задача~-- максимально быстрая отдача рассчитанного маршрута. Поддерживает построение путей через произвольное количество промежуточных точек для реализации режима мульти-вейпоинтов, маршрутизацию напрямую по географическим координатам и механизм временного бронирования емкости ребер для прогнозирования DUE. Не содержит логики симуляции.
    \item «Поставщик данных симуляции»~-- модуль, управляющий физикой движения агентов. Отвечает за расчет одномерной кинематики с учетом плотности потока, продвижение физического времени симуляции и трансляцию сырых параметров загруженности ребер графа.
    \item «Модуль принятия решений»~-- управляющий модуль, связывающий симуляцию и маршрутизатор. Он непрерывно отслеживает отклонение агентов от графика движения на основе метрики TTI, выявляет зарождающиеся заторы с помощью пространственных индексов и отправляет асинхронные триггерные запросы в маршрутизатор для локального или глобального перестроения путей движения.
    \item «Базовые структуры»~-- слой инфраструктуры, предоставляющий пулы рабочих потоков, безблокировочные очереди сообщений \cite{lock_free_queue, desrochers2015concurrentqueue}, общую диспетчеризацию фоновых задач и ядро симуляции, координирующее обмен данными между модулями.
    \item «Системная служба»~-- точка входа в программу, реализующая паттерн точки композиции зависимостей. Обеспечивает работу системного демона и внешний сетевой интерфейс на базе сокетов ZeroMQ, осуществляя асинхронную публикацию телеметрии и предоставляя REQ-REP API для управляющих команд.
\end{itemize}

Оркестратором процессов симуляции выступает класс \texttt{TrafficEngine}, координирующий взаимодействие остальных модулей. В начале каждого шага симуляции он инициирует продвижение физического времени и обновление кинематики агентов в модуле поставщика данных. После завершения физического шага измененное состояние симуляции передается в модуль телеметрии для трансляции внешним клиентам, а также отправляется в модуль принятия решений. Модуль принятия решений проводит анализ задержек на основе накопленной статистики и при необходимости формирует триггеры ремаршрутизации. Запросы на поиск путей поступают в пул потоков маршрутизатора, а полученные оптимальные маршруты фиксируются в менеджере объемов для динамического резервирования емкости ребер.

Инверсия управления и точка композиции зависимостей.
Связывание независимых подсистем осуществляется через паттерн внедрения зависимостей. Модули общаются исключительно через абстрактные контракты, такие как интерфейсы поставщика данных симуляции или публикатора телеметрии, ничего не зная о внутренней реализации друг друга. 

Сборка итогового конвейера симуляции происходит в единственной точке приложения — главной функции сборки, выступающей в роли корня композиции зависимостей \cite{butorin2026thread}. Оркестратор инициализирует объекты в строгой последовательности от ядра к периферии, формируя следующий главный цикл:
\begin{enumerate}
    \item Шаг симуляции: модуль симуляции продвигает физику движения на фиксированный временной шаг и формирует массивы изменений.
    \item Шаг телеметрии: извлеченные легковесные дельты изменений передаются в сетевой транспортный слой для асинхронной отправки на веб-клиенты.
    \item Шаг аналитики: модуль принятия решений забирает сгенерированные симулятором события-оповещения, включая критическое отклонение ожидаемого времени прибытия.
    \item Шаг маршрутизации: модуль принятия решений запрашивает у пула потоков альтернативные маршруты и возвращает их агентам.
\end{enumerate}

Данный подход превращает архитектуру в легко расширяемый конструктор, позволяющий в будущем при интеграции методов машинного обучения прозрачно подменить математический модуль принятия решений на нейросетевой инференс без переписывания транспортного ядра.

Эффективное объектно-ориентированное проектирование и организация данных в памяти.
Классический объектно-ориентированный дизайн с обильным использованием интерфейсов и виртуальных функций провоцирует промахи кэша инструкций процессора и блокирует агрессивное встраивание кода компилятором на этапе компиляции. В горячем цикле маршрутизатора это приводит к недопустимому нарушению бюджета времени в 190 наносекунд на одну итерацию обхода узла.

Для сочетания чистой архитектуры с максимальной аппаратной скоростью выполнения применена парадигма абстракций с нулевой стоимостью выполнения \cite{fog_optimizing_cpp}:
\begin{enumerate}
    \item Запрет на виртуальные вызовы: в методах обхода графа и симуляции физики полностью исключено динамическое связывание с использованием таблиц виртуальных функций.
    \item Инкапсуляция плоских данных: тяжелые массивы внутренних указателей строк и индексов столбцов компактного формата инкапсулируются внутри классов как приватные поля стандартного вектора. Внешний интерфейс предоставляет безопасные методы доступа, помеченные директивами компилятора для встраивания.
    \item Полиморфизм на этапе компиляции: компилятор полностью вырезает вызовы таких методов, заменяя их прямым ассемблерным смещением в оперативной памяти. Это гарантирует скорость выполнения на уровне языка ассемблера при сохранении строгой типизации и безопасности памяти современного C++.
\end{enumerate}
