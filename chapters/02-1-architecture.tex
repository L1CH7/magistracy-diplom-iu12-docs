\section{Архитектура программного ядра маршрутизации}

Разработанный программный комплекс представляет собой фоновую системную службу, разработанную в соответствии со стандартом C++20 \cite{iso_iec_14882_2020}. В отличие от классических монолитных транспортных симуляторов, архитектура ядра маршрутизации базируется на принципе строгой изоляции вычислительных контуров и отказе от сильной связности модулей \cite{butorin2026thread}.

Схема выделяет следующие ключевые компоненты:
\begin{itemize}
    \item Клиентское приложение на базе Qt и MapLibre: предоставляет графический интерфейс и визуализирует дорожную сеть с помощью векторных тайлов.
    \item Шлюз API Gateway / WS Proxy: координирует сессии, транслирует команды управления и телеметрию по протоколу WebSocket, а также предоставляет HTTP API.
    \item Вычислительное ядро Traffic Core: симулятор на C++, который выполняет шаг симуляции и рассчитывает маршруты. Ядро передает телеметрию через сокеты ZMQ.
    \item Модуль Data Processor: генерирует векторные MVT-тайлы на основе геоданных и формирует бинарный граф для симулятора.
    \item СУБД PostgreSQL с расширениями PostGIS и PGRouting: обеспечивает хранение картографических данных.
\end{itemize}

Функциональная декомпозиция модулей.
Для предотвращения усложнения кодовой базы и появления перегруженных классов, система физически разделена на изолированные библиотеки. Каждый модуль имеет собственный конфигурационный файл сборщика и инкапсулирует свою зону ответственности:

\begin{itemize}
    \item «Ядро симуляции» (\texttt{Traffic Engine})~-- центральный оркестратор, управляющий жизненным циклом симуляции и координирующий передачу данных между всеми подсистемами в рамках единого тактового цикла.
    \item «Поставщик данных» (\texttt{Data Provider})~-- модуль, управляющий физикой движения агентов. Он продвигает физическое время и рассчитывает одномерную кинематику с учетом плотности потока.
    \item «Маршрутизатор» (\texttt{Router})~-- вычислительный модуль без сохранения состояния, осуществляющий поиск кратчайших путей на графе с временной зависимостью. Поддерживает произвольное количество промежуточных точек и маршрутизацию по географическим координатам.
    \item «Менеджер объемов» (\texttt{Volume Manager})~-- компонент, отвечающий за резервирование и отмену пропускной способности ребер в пятиминутных временных интервалах для динамического перераспределения потоков.
    \item «Модуль принятия решений» (\texttt{Decision Engine})~-- управляющий контур, который отслеживает отклонение агентов от графика движения на основе метрики TTI, выявляет заторы и асинхронно отправляет триггеры ремаршрутизации.
    \item «Модуль телеметрии» (\texttt{Telemetry Module})~-- асинхронный публикатор текущего состояния дорожной сети и событий симуляции внешним потребителям по сети.
    \item «Офлайн-подготовка данных»~-- независимый контур, который импортирует геоданные, рассчитывает статические веса и оптимизирует структуру графа для её последующей загрузки ядром.
\end{itemize}

Взаимодействие компонентов в цикле симуляции.
Оркестратор \texttt{TrafficEngine} координирует главный цикл работы ядра, состоящий из следующих последовательных шагов:
\begin{enumerate}
    \item Шаг симуляции: \texttt{TrafficEngine} запускает физический шаг в модуле \texttt{DataProvider}. Модуль продвигает время симуляции, рассчитывает кинематику агентов и фиксирует изменения параметров ребер.
    \item Шаг телеметрии: \texttt{TrafficEngine} передает дельты изменений в модуль \texttt{TelemetryModule}, который асинхронно транслирует состояние сети внешним клиентам.
    \item Шаг аналитики: \texttt{DecisionEngine} считывает накопленную статистику задержек движения и выявляет заторы на основе метрики TTI.
    \item Шаг ремаршрутизации: обнаружив заторы, \texttt{DecisionEngine} запрашивает альтернативные пути у модуля \texttt{Router}. Маршрутизатор асинхронно рассчитывает кратчайшие пути с временной зависимостью и обновляет бронирования в \texttt{VolumeManager}.
\end{enumerate}

Инверсия управления и абстракции нулевой стоимости.
Внедрение зависимостей изолирует подсистемы друг от друга. Модули взаимодействуют исключительно через абстрактные контракты, не завися от внутренней реализации соседа. Главная функция приложения собирает итоговый конвейер симуляции, выступая в роли корня композиции зависимостей \cite{butorin2026thread}. Такая структура упрощает расширение системы: замена модуля принятия решений на нейросетевой инференс не требует изменения транспортного ядра.

Вычислительное ядро совмещает модульную архитектуру с высокой аппаратной скоростью C++, используя парадигму абстракций с нулевой стоимостью выполнения \cite{fog_optimizing_cpp}. Ядро исключает динамическое связывание через таблицы виртуальных функций из критических путей симуляции и обхода графа. Вместо этого компилятор выполняет полиморфизм на этапе сборки и встраивает методы доступа к плоским структурам данных непосредственно в точки вызова. Этот подход сохраняет строгую типизацию и устраняет накладные расходы времени выполнения.

Для минимизации накладных расходов на переключение контекста процессора и предотвращения деградации L1/L2-кэшей из-за миграции вычислительных потоков планировщиком операционной системы, в разработанном ядре реализован механизм аппаратной привязки потоков (CPU Affinity). Привязка осуществляется при инициализации пула потоков маршрутизации с использованием системных вызовов POSIX-совместимых операционных систем \texttt{pthread\_setaffinity\_np} \cite{iso_iec_14882_2020}. В соответствии с конфигурацией сборки CMake, логика распределения ядер выглядит следующим образом:

\begin{enumerate}
    \item Физическое ядро 0 (логические CPU 0 и $N/2$, где $N$~-- общее число логических ядер процессора с учетом Hyper-Threading/SMT) полностью резервируется под операционную систему.
    \item Поток основного цикла симулятора (\texttt{TrafficEngine}) и управляющий контур принятия решений (\texttt{DecisionEngine}) привязываются к логическому CPU 1 (первому потоку физического ядра 1).
    \item Асинхронный диспетчер маршрутов и поток отправки сетевой телеметрии (\texttt{TelemetryModule}) привязываются к логическому CPU $1 + N/2$, являющемуся SMT-сиблингом первого физического ядра.
    \item Вычислительные потоки-воркеры пула маршрутизации (\texttt{RouterWorker}) жестко привязываются попарно к логическим ядрам со второго физического ядра (CPU 2) до последнего (CPU $N/2 - 1$ и CPU $N - 1$).
\end{enumerate}

Применение такой схемы привязки потоков гарантирует стабильность L1/L2 кэш-линий для локальных данных очередей приоритетов и предотвращает непроизводительную инвалидацию кэша L3 при конкуренции потоков на общем физическом ядре в условиях SMT.

Для межпоточного взаимодействия и передачи задач от управляющего контура к пулу потоков-маршрутизаторов применяются высокопроизводительные безблокировочные очереди MPMC (Multi-Producer Multi-Consumer) \cite{desrochers2015concurrentqueue}. Несмотря на устранение системных блокировок на уровне передачи данных, на верхнем уровне диспетчеризации используется барьерная синхронизация пакетов задач. Данный барьер критически необходим для обеспечения темпорального детерминизма: главный цикл симуляции приостанавливает продвижение физического времени до тех пор, пока все агенты, запросившие ремаршрутизацию на текущем такте, синхронно не получат новые пути. Хотя такой подход вводит потенциальную уязвимость к эффекту «длинного хвоста», когда один медленный расчет задерживает ответ по всему пакету, крайне низкое среднее время поиска пути в алгоритме $ALT$ и микросекундные задержки доступа самих безблокировочных очередей нивелируют этот недостаток, не приводя к деградации общей пропускной способности симулятора.
